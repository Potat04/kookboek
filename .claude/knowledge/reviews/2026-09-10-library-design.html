Sections of the book: how the library holds labels

Labels are decided. What was still open is how the main screen carries them once there are a hundred, two hundred, three hundred recipes, without turning a book into a search box.

Anton's question: "Labels but the main screen must be extended to perhaps allow folders or whatever." Judged against the paper-cookbook vision, the contrast and typography rules, one-handed phone use, and building it in Compose with no new dependency.

Who was asked

Six haiku agents, each given one persona, read access to the code and the UX rules, and the same open question. None of them talked to each other. Where several landed on the same shape independently, that shape is probably right.

K · the collectorThree hundred recipes, half never cooked. Wants structure without a filter panel.
O · the older readerLarge text, one hand, tremor. Cooks in Dutch, prints things.
F · the family memberGot the APK from Anton. Grandma's cards, WhatsApp screenshots. Not technical.
C · the weeknight cookPhone on the counter, hands in the dough. Wants "what to cook" in ten seconds.
P · the switcherUsed Paprika, Mealie, Tandoor. Knows which organizing features die after a week.
J · the kid who bakesEleven years old, mostly wants to look at cake pictures. No patience for setup.

What they converged on

Five of six, independently, described the same shape: a row of tappable label chips sitting under the existing favourites-and-sort row, filtering the list below in place, with "All" as a permanent way back. Nobody proposed a second screen for browsing. Nobody wanted labels printed onto the recipe card. Everyone wanted assigning a label to happen from the existing long-press selection, not a new gesture.

K and O both asked for a count next to each label, so a section reads as "how big is this" before you tap it, the way a table of contents shows page ranges. F and C both warned that hiding the feature behind a toggle or a collapsed panel means it gets forgotten, which is exactly what C predicted for the one idea (a "Browse by label" toggle) that hid it. P's contribution was the sharpest constraint: in Paprika and Tandoor, exclusive categories caused mis-filing, because a recipe is never really "just one thing", and that is why this app already decided a recipe holds several labels rather than one folder.

Candidate layouts, and a verdict for each

Chip row under the search field

fits, chosenK, O, F, C, P, and the decision already on record

A horizontal, scrollable row of label chips directly under the existing favourites/sort row, single-select, "All" pinned first, each chip carrying a count. Tapping filters the list in place; tapping again, or tapping "All", clears it.

This is what nearly every persona asked for without being shown it first, and it is a small, reversible addition to a row that already exists. The open part is what happens once there are more labels than fit on one screen, which the chosen design below answers with an overflow entry rather than a second row.

Grouped list with sticky section headers

rejected as defaultK's second idea

Recipes shown under label headings, "Weeknight", "Desserts", each collapsible, the way K described "chapters, exactly like a printed cookbook where you've written section headings in the margin."

The image is right but the mechanics fight the data model. A recipe can carry several labels, so a permanent grouped view either repeats a recipe under every label it has (a 300-recipe library could show 500+ card-renders) or picks one label to group by, which reintroduces the exclusive-folder problem P warned against. It survives as the presentation inside the labels overview described below, where it lists labels, not recipes, and duplication does not apply.

Folder-like label pages, a new destination per label

rejectedimplied by "folders" in Anton's own question

Tapping a label pushes a new screen, its own back stack, the way a folder opens in a file browser.

Navigation-compose has four destinations today and the architecture notes are explicit that the app stays small on purpose. An in-place filter gives the same result, one tap to enter and one tap to leave, without a fifth destination, a new back-stack case, or a state to restore on rotation. Nothing a folder page would show that the chip row and the list below cannot.

A "browse by label" toggle, two-level home

rejectedC's second idea, and C's own objection to it

The label row only appears after tapping a button to reveal it, keeping the normal screen uncluttered.

C proposed this and then talked themselves out of it in the same answer: "I'd probably find it annoying because it's hidden by default, I'd forget it's there." A feature that has to be remembered before it can be used will not get used. The chip row has to be visible every time there is at least one label, not opt-in.

Horizontal shelves per label, a row of cards for each

rejectednone asked; considered and dropped

A vertically scrolling stack of horizontally scrolling rows, one per label, the pattern every streaming app uses for genres.

This is the one idea that looks most like a "dashboard home screen with recently cooked, suggested for tonight" that the previous review already rejected outright: "the library is the home screen, it's a book, not a feed." It is also the heaviest to build (nested lazy lists) and the hardest to keep at the contrast and width limits already documented for a single card, multiplied by however many shelves are visible.

Multi-select label chips (OR across several at once)

deferredP

Tap "Vegetarian" and "Weeknight" together and see recipes that carry either.

Reasonable, and explicitly the thing to add later if single-select turns out to be limiting. For a first version it complicates the one sentence a reader should be able to say about what they are looking at ("I'm looking at Weeknight"), which is exactly the clarity K asked for. Single-select ships first; the state shape (an active label, not a set) does not block adding multi-select later.

The chosen design

A label row, single-select, always visible once a label exists, with a small overflow sheet that acts as the book's table of contents once the row cannot hold everything. Label assignment happens from the existing long-press selection, as already decided, through a sheet that only ever adds.

Top to bottom of the screen

Masthead is unchanged when nothing is selected: logo, app name, recipe count, the settings gear.

SearchField is unchanged.

FilterRow is unchanged: the favourites chip and the sort dropdown, on one line.

LabelRow, new. A horizontal, scrollable row directly under FilterRow, present only when total > 0 and the library has at least one label. Chips, left to right:

  • "All", always first, always present. Selected by default and whenever no label filter is active.
  • "Unlabelled", present only when at least one recipe carries no label. Filters to exactly those, so a reader working through a backlog of unsorted recipes has a visible way to find them, without the app inventing the concept of a "label" for having none.
  • One chip per label the reader has created, sorted by how many recipes carry it, most first, ties broken alphabetically. Each chip reads as Name · count, e.g. "Weeknight · 24", the way O and K both asked to judge a section's size before opening it.
  • "More…", appended whenever there are more than six real labels (a fixed threshold, not a width measurement, so the row's contents never shift depending on font scale). Opens the labels overview sheet described below.

A chip uses the same FilterChip treatment the favourites chip already uses: primaryContainer fill and onPrimaryContainer text when selected, labelLarge type, MaterialTheme.shapes.small. Tapping the active chip again, or tapping "All", clears the filter. Only one label filter is active at a time; it combines with favourites-only and the search text exactly the way those two already combine with each other, by narrowing the same list further.

The list below is unchanged in kind: EmptyLibrary, NoMatches, or RecipeCard items. NoMatches gains a third wording for "nothing in this label" alongside its existing "nothing found" and "no favourites match" cases. RecipeCard itself does not change. No label chip is drawn on the card. The card is already at the width the notes describe as its limit, where a slightly longer meta line was enough to truncate "15 stuks"; a label badge would cost exactly that room, for information the LabelRow above already states more clearly than a small chip on fifty cards could.

A recipe with no label looks identical to one with several, in every view except when a specific label or "Unlabelled" is the active filter. There is no "no label" marker to design, because there is nothing to say about it that the reader has not already said by not labelling it.

Selection bar: the rule broken on purpose

The UI notes are explicit that selection mode offers exactly the two actions a single recipe's own menu offers, refetch and delete, so nobody has to remember a third way of doing something. The previous feature review already flagged labels as the one exception worth making, and this is where it happens.

The bar becomes: close (×), the "N selected" count, a new label action, then refetch, then delete, in that order. Delete stays rightmost and stays the one action with MaterialTheme.colorScheme.error, exactly as today, so the position and colour a reader has already learned to be careful with does not move. Label sits between the count and refetch: the safe, non-destructive, most likely to be chained with other work.

The icon set the app already imports is material-icons-core, not the extended pack, and core does not carry a tag, label, folder or bookmark glyph (checked against the actual jar, only List exists among the plausible candidates, and it reads wrong for this). Rather than pull in material-icons-extended for one icon, add a small custom vector drawable the same way ic_logo.xml already exists, tinted through Icon(tint = …) so it follows the palette for free.

The label picker sheet

Tapping the label action opens a bottom sheet titled for the count of recipes selected. It only ever adds; it does not show or let you clear labels some of the selected recipes already carry, because a tri-state "some have this, some don't" checkbox is exactly the kind of fiddly control O and F both said they would get wrong under pressure. Removing a label from one recipe is a job for that recipe's own screen, not this sheet; it is out of scope for the main-screen work here and is noted for whoever builds the recipe-detail side of labels.

Inside the sheet, top to bottom:

  • The reader's existing labels as plain, tappable chips (unselected style, since this is add-only and starts blank every time). Tapping toggles it into the "will be added" state, filled like a selected FilterChip.
  • A thin divider and "Suggestions from these recipes" — the union of every tags entry across the selected recipes, minus any that already match a label name. Shown as outlined, dashed chips, visibly different from real labels, so nobody mistakes a suggestion for something already organized. Tapping one creates the label and marks it toggled on in the same motion; it never happens on its own. This answers directly how tag suggestions surface: only here, only on demand, never turned into a label without a tap.
  • A "+ New label" chip at the end that opens a single-line text field for a name the tags did not suggest.
  • "Done" applies every toggled label to every selected recipe, clears the selection, and closes the sheet, matching how delete and refetch already end a selection. A toast confirms ("Labels updated") without naming every label or every recipe, since a bulk action across a dozen recipes and three labels does not fit one readable sentence.

When there are no labels yet and no tags to suggest, the sheet shows one quiet line inviting a name to be typed, rather than an empty list that looks broken.

The labels overview, the book's table of contents

The "More…" chip, and this is the direct answer to "folders or whatever": a bottom sheet listing every label as a row, name and count, tallest first. Tapping a row does exactly what tapping its chip would have, filters and closes. This is where Anton's instinct for something folder-shaped gets satisfied without an exclusive folder: it is a page you flip to that lists every section of the book, not a place recipes are filed one level deep.

Each row also carries the only two label-management actions this design needs: rename and delete, as a pencil and a bin at the row's end, mirroring the pattern the app already uses elsewhere of putting an action next to what it acts on rather than behind a menu. Deleting a label removes it and its associations, not any recipe; ideally this follows the same immediate-delete-plus-undo-snackbar pattern the app uses everywhere else instead of a confirmation dialog, but that depends on the label data layer, built separately, exposing enough to restore a deleted label with its recipes reattached. If that turns out not to be practical in the first pass, a plain confirm dialog is the acceptable fallback for this one destructive action, and it should be revisited once the data layer supports it.

A label that reaches zero recipes (its last recipe was unlabelled, or deleted) drops out of the LabelRow automatically, since a chip for an empty section has nothing to open, but stays listed in the overview sheet with a "0" count, so the reader can reuse the name later or delete it deliberately instead of it vanishing on them.

Empty states

  • No recipes at all. EmptyLibrary is unchanged; there is nothing to label yet.
  • Recipes exist, no labels created. The LabelRow does not render. No placeholder chip, no "create your first label" banner. The feature announces itself the first time someone long-presses a card and sees the new label action in the selection bar, the same quiet-discovery approach the existing selection mode already uses.
  • A label with matches removed by search or favourites. NoMatches gains a label-aware line: "Nothing in 'name'" alongside the existing "Nothing found" and "No favourites match that", following the same pattern.
  • "Unlabelled" filter selected and everything already has a label. The chip simply is not shown, per the rule above, so this state cannot be reached.

One paragraph for landscape and tablet

The previous review already proposed a two-column library grid at width and a two-page layout for the recipe screen itself; the LabelRow extends the same idea rather than competing with it. At a wide window size class, move the label list from a horizontal scrolling row into a persistent vertical rail down the left edge, one label per line with its count, "All" and "Unlabelled" at the top, functioning as a literal table-of-contents column beside the card grid, the same relationship a real cookbook has between its index and its pages. The overview sheet becomes unnecessary at that width, since the rail has room to show every label without an overflow; the rename and delete affordances that live in the sheet on a phone move onto the rail's rows directly. This is a layout decision for whoever builds the width-class work, not a rebuild of the LabelRow's logic, which stays the same activeLabel state either way.

Where the personas were wrong

  • "Maybe a 3-dot menu already exists on the selection bar." F hedged this while guessing where a label action might go. It does not: SelectionBar today is exactly close, count, refetch, delete, no overflow menu anywhere in it.
  • The implicit worry that notes and tags are not searched today. P asked for search across "title, ingredients, labels, notes... as one thing." Recipe.searchBlob() already includes title, site, author, description, tags, ingredients and notes. The only new field search needs once labels exist is the label names themselves; everything else P asked for is already there.
  • O's request to print a label's recipes. Not a wrong claim about the code, but worth separating from this task: there is no print feature in the app at all yet. The previous review already recommends one ("Print, or save as PDF") independent of labels; extending it to a whole label is a natural follow-on once that exists, not part of this design.

One thing that was not wrong and matters for the implementation: the current KookboekViewModel.selected() computes the acted-on recipes as visible.value.filter { it.id in _selection.value }. That is fine today because changing the search text or the favourites toggle mid-selection is rare. Once a label chip sits above the list and is meant to be tapped while recipes are selected, this stops being an edge case: switching the active label filters a selected recipe out of visible, and it silently drops out of what refetch, delete, or the new label action touches, while still showing as selected the moment the filter is undone. selected() should filter from all.value, not visible.value, so a selection survives whatever the LabelRow or search field does above it. This is a small change, but it is worth making at the same time as the LabelRow, not after someone loses a batch delete to it.

Rejected, and why

  • Literal exclusive folders, one recipe in one place. Contradicts the data model already decided (a recipe holds several labels) and is the specific pattern P said caused mis-filing and abandonment in Paprika and Tandoor.
  • Labels drawn on the recipe card. The card is already at the width the notes call its limit; a label chip costs the room "15 stuts" already needed once.
  • A default view grouped by label with sticky headers. Duplicates cards for multi-label recipes or forces an exclusive "primary label", both wrong for this data model. Survives only as the flat, recipe-free list of labels in the overview sheet.
  • A separate navigation destination per label. A fifth destination and a new back-stack case for something an in-place filter already does in one tap.
  • Hiding the label row behind a toggle. C proposed and then rejected this in the same breath: hidden means forgotten.
  • Horizontal shelves per label ("genre rows"). The exact shape of the "dashboard home screen" the previous review already ruled out: a feed, not a book.
  • Auto-creating labels from tags without a tap. F and J both worried about "weird" or presumptuous labels appearing on their own. Tags are suggestions only, shown in one sheet, and become a label solely on a tap.
  • Tri-state bulk label editing (add and remove together across a mixed selection). Correct in theory, confusing in practice for exactly the readers who most need selection mode to be predictable. The bulk sheet only adds; removing one recipe's label is a job for its own screen.
